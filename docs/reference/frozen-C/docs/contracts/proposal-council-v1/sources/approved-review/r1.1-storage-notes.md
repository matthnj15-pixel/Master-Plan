# R1.1 storage protocol: source evidence and browser boundary

This supports the four targeted R1.1 changes. It is document research, not an implementation or a passing two-tab test. Code baseline remains `18dded6207f7217021d84b42aad6cc8e00b68f43`; the approved first-slice scope and private recovery defaults do not change.

## Existing source behavior

| Evidence at the audit baseline | Consequence for R1.1 |
|---|---|
| `src/ui.js:19` chooses browser `masterplan.dev.save` and account `save-dev` for Dev. | Reusing those paths for v4 would expose v4 data to pre-v4 code. Isolate both the browser key and account document, leaving the legacy source as a separate branch. |
| `src/ui.js:45` writes the complete current state without another tab's persisted-revision check; `:47–48` performs account writes. | A new in-memory revision alone does not prevent an older tab from replacing a newer saved snapshot. Every current writer must use the same physical-save-slot protocol. |
| `src/ui.js:50` returns null for unsupported saves, while `src/engine.js:740` supports only versions 1–3. | An old build cannot be taught a new v4 guard through the v4 file itself. New code must preserve unknown formats, and old deployments must never share the v4 output path. |
| `src/ui.js:73–74` selects a newer account snapshot by `savedAt`. | A newer legacy timestamp is not permission to overwrite or reimport over an existing v4 branch. |
| `src/offline-worker.js` selects cached/network shells and removes previous shell caches. | A shell rollback/cache policy is not a save-format protection mechanism. Do not depend on old code recognizing a new fence or on a compatible old shell always being available. |

These are static source observations. They do not claim the current two-tab race has been reproduced through normal browser interaction.

## Browser API evidence

The HTML Standard tells authors to assume no locking when using shared localStorage state; a read/check/write sequence does not form a cross-tab compare-and-swap. R1.1 therefore needs actual write coordination rather than a timestamp or storage-event heuristic. [WHATWG Web Storage introduction](https://html.spec.whatwg.org/multipage/webstorage.html).

Web Locks provides exclusive named locks across cooperating tabs/workers of the same origin. Its callback promise controls the lock lifetime, and availability is subject to the execution context. The protocol must use one stable name for the physical save slot, including resets and migrations; using a name derived only from the current game ID would split writers when a game is replaced. [MDN Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API), [LockManager.request](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/request).

## Required application properties

- Model inference stays outside a save lock. A current writer acquires the exclusive slot lock, rereads the authoritative persisted snapshot, verifies its storage generation and game/revision/format, checks replay identity and all required gates, then prepares and atomically writes the next complete snapshot before publishing success.
- A queued stale writer reloads and asks for a fresh preview; it never writes its older snapshot over a newer one. Storage events or broadcasts can speed refresh, but they are not the correctness mechanism. No timeout lease or lock stealing is an accepted fallback.
- Lock unavailability or storage failure cannot become a reported successful durable action. Preserve the public saved state and private input; report the actual storage boundary. The test specification must include two pages sharing one browser storage context, reordered attempts, reload/replay, and replacement/migration cases.
- Updated code checks the storage format independently of the experimental gameplay flag. A v4 save survives flag-off and unsupported-reader paths without automatic downgrade, reset, deletion, or projection into a legacy output key.
- A pre-v4 deployment may continue its own legacy branch, but cannot address the v4 namespace. Restoration of a compatible build discovers the preserved v4 branch first. No claim is made that an old deployment can resume v4 gameplay.
- Account replication is separately versioned and never grants an older/equal conflicting account snapshot authority over newer local state. Same-origin coordination does not claim a distributed cross-device transaction or repair browser storage eviction.

The canonical protocol, exact save paths, receipt fields, required-gate semantics and planned tests are in the revised contract and fixture specification. Executable assertions come from Builder D after contract freeze; browser QA later runs the real two-tab flow against the exact integrated revision.
